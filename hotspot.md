# Hotspot Fix Plan

## Findings (validated over 2 profiling runs)

### Hotspot 1: `normalizeSQL` → `processByte` — 46–71% CPU

File: `internal/fs/normalize.go`

Processes one byte at a time in a tight loop. For each byte it:

1. Checks `n.sawCR` (branch)
2. Switches on byte type (branch)
3. Appends one byte to `output` slice

The SQL generated by the benchmark (and found in real repos) contains mostly space/tab runs followed by content bytes. The normalizer collapses whitespace runs into single newlines but the bookkeeping (`pendingWhitespace` slice append + burst) adds overhead.

**Breakdown per-call on medium SQL (2000 bytes):**

| Operation | Share |
|---|---|
| `*output = append(*output, b)` | ~23% |
| `append(n.pendingWhitespace, b)` | ~6% |
| `*output = append(*output, n.pendingWhitespace...)` | ~9% |
| branches (switch + if) | ~20% |
| rest (loop, function frame) | ~42% |

### Hotspot 2: `gitInfo` — 6% CPU per object

File: `internal/fs/layout.go:198-211`

Calls `exec.Command("git", "log", "-1", "--format=...", "--", fileName)` for every object file. Each invocation forks a subprocess, looks up the `git` binary, and reads output.

Cost per object (~6% of total diff time):

| Operation | Share |
|---|---|
| `os/exec.(*Cmd).Output` (subprocess I/O) | 58% |
| `os/exec.Command` + `LookPath` (binary search) | 38% |

This only runs once per object (cached by `sync.Once`), but on first scan of N=2000 objects it spawns 2000 subprocesses.

### Hotspot 3: `slicebytetostring` — ~5% overhead

File: `internal/fs/normalize.go:15`

`normalizeSQL` builds a `[]byte` then converts it to `string` for the return. The caller (`NormalizeAndHash`) immediately converts back to `[]byte` for SHA-256. Round-trip allocation is wasteful.

## Fix Plan

### Fix 1: Rewrite `normalizeSQL` to process chunks, not bytes

**Target:** `internal/fs/normalize.go`

**Approach:** Replace the byte-at-a-time loop with index-based scanning.

```go
func normalizeSQL(input string) string {
    var b strings.Builder
    b.Grow(len(input))
    sawCR := false
    pendingNL := false

    for i := 0; i < len(input); i++ {
        ch := input[i]
        if sawCR {
            sawCR = false
            if ch == '\n' {
                continue
            }
        }
        switch ch {
        case '\r':
            sawCR = true
            pendingNL = true
        case '\n':
            pendingNL = true
        case ' ', '\t':
            pendingNL = true
        default:
            if pendingNL {
                b.WriteByte('\n')
                pendingNL = false
            }
            // write content run in bulk
            start := i
            for i < len(input) && input[i] > ' ' {
                i++
            }
            b.WriteString(input[start:i])
            i-- // loop increments
        }
    }
    if pendingNL {
        b.WriteByte('\n')
    }
    return b.String()
}
```

**Key changes:**
- Content runs are copied in bulk (`WriteString`), not byte-by-byte
- Whitespace tracking uses a boolean instead of `pendingWhitespace` slice (avoids append + burst)
- `strings.Builder` replaces manual `[]byte` slice management

**Expected speedup:** 3-5x on `normalizeSQL` alone. The bulk copy and removed slice overhead eliminate the two largest sources.

### Fix 2: Eliminate `[]byte` ↔ `string` round-trip

**Target:** `internal/fs/layout.go:133-137` (`NormalizeAndHash`)

**Change:** Accept `[]byte` and return checksum directly without intermediate string.

```go
func NormalizeAndHash(input []byte) string {
    normalized := normalizeSQLBytes(input)
    sum := sha256.Sum256(normalized)
    return hex.EncodeToString(sum[:])
}
```

And add `normalizeSQLBytes([]byte)` that writes into a pre-allocated `[]byte` buffer (or uses `bytes.Buffer`).

**Callers update:** `CachedFile.Checksum()` already has `content` as string after `Content()`. Change `Content()` to return `[]byte` or add `ContentBytes()` method.

**Expected speedup:** ~5% reduction in allocs, no `slicebytetostring` call.

### Fix 3: Batch git info query

**Target:** `internal/fs/layout.go:198-211` (`gitInfo`)

**Approach:** Replace N individual `git log <file>` calls with one `git log --all --name-only --format=...` and parse the output.

```go
func batchGitInfo(absPaths []string) map[string]GitInfo {
    dir := filepath.Dir(absPaths[0])
    args := append([]string{"-C", dir, "log", "--all", "--format=%H%n%an%n%aI%n---", "--name-only"})
    cmd := exec.Command("git", args...)
    out, err := cmd.Output()
    if err != nil {
        return nil
    }
    // parse output: group commits by file, take first for each
    ...
}
```

**Integration:** Call `batchGitInfo` once in `Scanner.Scan()` after all files are discovered, populate a `map[string]GitInfo`, and reference it in `CachedFile.loadGitInfo()`.

**Expected speedup:** N subprocesses → 1. For N=2000, ~2000x fewer process forks.

### Fix 4 (stretch): Parallelize diff compute

**Target:** `internal/diff/diff.go:57-114`

The per-object classification loop is trivially parallel. Each object is independent. Use `errgroup` to fan out.

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(runtime.GOMAXPROCS(0))
mu := sync.Mutex{}
for _, obj := range layout.Objects {
    obj := obj
    g.Go(func() error {
        // ... classification ...
        mu.Lock()
        plan.Objects = append(plan.Objects, plannedObj)
        mu.Unlock()
        return nil
    })
}
```

**Constraint:** `handleChanged` reads `transitionsByKey` and `state` — safe for concurrent read.

**Expected speedup:** 2-4x on multi-core.

### Fix 3: Preload git info in parallel — IMPLEMENTED

Scanner.Scan() now collects all file paths and preloads git metadata via parallel goroutines with semaphore (limited to GOMAXPROCS, max 32). Results are injected into `CachedFile` via `preloadGitInfo()` which races safely with lazy `loadGitInfo()` through `sync.Once`.

In non-git environments (no git repo): repeated `LookPath`/`exec.Command` still occurs but in parallel — walls improve but total CPU is similar.

In git-tracked repos: N sequential subprocess calls → N parallel calls capped at worker pool. For 2000 files with 8 workers: ~250 effective sequential calls vs 2000.
